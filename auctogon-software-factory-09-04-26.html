The division

What a person actually does

Every human act on this list is a decision or a specification. None is production.

Humans do
  • Decide what the product should do — and say when it's wrong
  • Define the architecture
  • Approve the implementation plan, before any code exists
  • Rule on findings that need judgement: business rules, tradeoffs, safety
  • Sign off on product and on engineering, then press the button that releases
Humans never
  • Write production code, a test, or a database migration
  • Read a pull request line by line — six specialist reviewer agents do that
  • Do manual QA
  • Chase a build failure, a lint error, or a merge conflict
  • Wave through their own work

The premise

Specification first

Agents are fast and literal. Given a vague brief they produce something plausible and subtly wrong. So the specification is written first — at four altitudes, down to the procedure the agent itself follows — and the implementation is derived from it rather than invented alongside it.

Altitude 1

Architecture

51 decision records. How the system is built and why — signed by a named human before code follows.

Altitude 2

Rules

78 rules translating those decisions into shapes an agent must produce and shapes that fail review.

Altitude 3

Behaviour

Numbered acceptance criteria per ticket, written as start state → action → expected result so a machine can run them.

Altitude 4

Process

37 written procedures — the steps the agent takes to do any of the above, specified as carefully as the code they produce.

Altitude 1, up close

How an architectural decision gets made

A decision record holds the decision, the reasoning, and the alternatives that lost — so nobody re-proposes them next quarter. This is the layer people guard most closely.

Step 1

The gap surfaces

Before large work, an agent surveys all 51 records and returns one line per relevant one — typically two to six. Work needing a decision none of them covers is reported as a gap, not assumed.

Step 2

Drafted & signed

An agent drafts; a named human signs. Nothing proceeds on implied approval, and the signature goes on the record with a date.

Step 3

Reviewed like code

Records go through the same review gate as source. Weakening a non-negotiable rule without recorded consent is a merge-blocking finding.

Step 4

Never deleted

Draft → Accepted → Superseded. A superseded record keeps its number and its text, so how the current answer was reached stays readable.

Altitude 2, up close

Implementation isn't free-form either

The agent doesn't choose how to build. 78 written rules say which shapes are correct and which fail review — how data is fetched, where business logic may live, what an error must do, which component a form must use.

Loading

16 rules are always in mind. The other 62 are scoped to file paths and load only when a change touches their area — nobody reads database rules to edit a button.

Enforcement

Each rule is caught at the cheapest place that can catch it: the compiler, then ~40 automated checks, then a review lane, and only then a person.

Draining

Touch means migrate. Edit a file still written the old way and you convert it in the same change — so debt shrinks with every piece of work rather than being frozen.

Conflicts

Surface, don't average. When two patterns disagree, the agent picks one, says why, and flags the loser — never writes something that satisfies both.

Altitude 4, up close

Every step is a skill, so every step repeats

An agent asked to "ship this" would improvise, and improvise differently each time. So nothing is asked in the abstract. Each stage of the line is a skill — a written procedure with numbered phases, hard rules, guardrails and edge cases — and the agent executes it rather than inventing one.

Same every time

The procedure is the same whoever runs it, whenever, on whatever model. Quality stops depending on how well the request happened to be phrased that morning.

They compose

Skills call skills. Building invokes planning, then shipping; shipping invokes review, then the pull-request loop. A person types one word and a chain of specified steps runs.

Stops are written in

Each skill names its own stop-and-ask points. "Never merge without confirmation" isn't a habit someone remembers — it's a step in the procedure that has to be executed.

Improved once

A lesson learned becomes an edit to the skill, not tribal knowledge. Fixing it once fixes every future run — and the fix is reviewed like any other change.

The line

Seven stages, front to back

Each stage names the skill that runs it. Amber marks a point where a person must answer before anything moves.

1

Scoping a project

/add-project/adrA body of work is defined before any of it is split up
  • The agent can't proceed until it can restate the problem and the requester agrees with the restatement.
  • A plain-English brief, then a technical analysis written after the architecture survey — so the design is made inside the decisions, not against them.
  • An inventory of everywhere the affected concept already lives. This routinely inverts the scope: "wire up four screens" becomes "delete from three."
Human Product lead signs the brief. Tech lead signs the analysis. Hard stops — approval of something else doesn't count.
2

Filing a feature or a bug

/add-feature/add-bugOne unit of work becomes one ticket
  • The agent infers area, size and priority, then drafts numbered acceptance criteria phrased so a machine can execute them later.
  • Bugs also get a duplicate check and a regression list: what nearby thing should I prove still works?
Human Features are shown as a draft for approval. Bugs file immediately — a report is cheap, losing one is expensive.
3

Building it

/implement-feature/bugfix/planExplore, plan, then write — never the other way round
  • The agent claims the ticket and follows one of two procedures: one for features, another for bugs. The agent checks that defects are reproducible and facts in the ticket are still true.
  • It writes a plan naming actual files. The plan is approved before a line of production code exists.
  • Tests come next and they fail. At a minimum, every AC needs a failing test. The implementation's job is to turn them green.
  • Before handing off it walks every criterion against the running application.
  • Any discoveries found during the build are added to the ticket to be reviewed by future steps.
Human The plan is approved explicitly — "just do it" doesn't skip it. Also: how to isolate the work, and any criteria discovered while building.
4

Preflight — review before anyone else sees it

/preflightSix specialist reviewers read the change in parallel, locally
  • A classifier decides which specialists are relevant — a copy edit doesn't wake the database reviewer.
  • Each runs as its own agent, with its own checklist and no sight of the others' findings.
  • Findings split into mechanical and needs a human. Mechanical ones are fixed on the spot; the rest stop and ask.
Human Decide what to do about any discovered issues where the fix is not mechanical: fix now, file for later, or overrule.
5

Pull request & the review gate

/deploy/review-prThe same six reviewers run again in the cloud, plus the mechanical checks
  • The request opens with a test plan carrying the ticket's own criteria IDs, so what gets verified traces back to what was asked for.
  • An aggregator tallies the six lanes and blocks the merge on anything serious.
  • Alongside them, ~40 deterministic checks — forbidden patterns, database safety, style. Those checks have their own tests, so a check can't quietly stop checking.
Human The merge. An agent never merges without being asked.
6

QA — automated, deliberately at arm's length

/ready-for-qa/notion-qaA second agent tests the shipped change on a live environment
  • A queue drains every fifteen minutes: pick the ticket, find the merged work by its ID, drive a real browser through the criteria on the live development site.
  • Each criterion gets pass, fail, or couldn't test, with expected-versus-actual on failures.
  • The testing agent has no access to the ticket system. A separate step records the verdict — so it structurally cannot grade itself.
Human None, by design.
7

Sign-off & release

/product-signoff/tech-impl-summaryTwo people, two questions, then promotion
  • Product: criterion by criterion — does this actually solve the problem someone reported?
  • Engineering: what shipped, which patterns it used, whether it honours or violates the written decisions, and an honest critique of what could have been done better.
  • Only when both are checked does the ticket close. Staging and production are separate, manual, one-click promotions.
Human Both sign-offs, and both promotions. Nothing reaches customers on an agent's initiative.

Highlighted skill #1

/review-pr — fan the change out to six specialists

One reviewer reading for everything reads for nothing in particular. A classifier routes each changed file to the specialists that can judge it, they run at once with no sight of each other's findings, and every finding is posted as an inline comment on the exact line.

Highlighted skill #2

/adr — survey the architecture before planning

Before any sizeable piece of work, the agent reads the architectural record — but reading 51 documents in full would drown the session before it starts. The procedure is a funnel: skim everything cheaply, read the few that matter properly, and emit a checklist.

Step 1 · Skim

One token-efficient pass over a short summary of every ADR.

Step 2 · Triage

Sorted against the task. When in doubt, keep — a missed constraint costs more than an extra read.

Step 3 · Read

The survivors read in full, with their paired enforcement rules.

Step 4 · Output — one imperative line per constraint. Pastes straight into the plan.
